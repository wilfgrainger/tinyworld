# v0.6.1 Visual Rescue

**Status:** active corrective release  
**Baseline:** merged v0.6.0 Target-State Consolidation  
**Profile schema:** 11, unchanged

## Why this release exists

v0.6.0 added substantial life-sandbox foundations, but the first observed screenshots exposed a serious presentation mismatch between the written TinyWorld quality bar and the rendered game.

The runtime currently includes prototype visual mechanisms that should never have represented finished player-facing art:

- primitive welded Part hair and shoes;
- large always-on-top information panels over ordinary world objects;
- HUD/navigation chrome that competes with the world;
- civic destinations and landmarks whose text explains more than their physical form;
- hero buildings and objects that still read too strongly as fallback geometry.

v0.6.1 fixes those problems before the roadmap moves on to broader Village Life expansion.

## Release thesis

> **A player should understand TinyWorld by looking at the world, not by reading developer-shaped panels floating over it.**

The visual direction combines broad principles only:

- Brookhaven-level world readability;
- Toca-style tactile warmth and playful object clarity;
- Ready Player One-style contrast and wonder for impossible worlds;
- original TinyWorld characters, buildings, props, layouts and UI expression.

## Workstream A - Prototype removal

### Character

- remove the primitive `CharacterAppearanceBuilder` hair/shoe geometry from normal play;
- preserve the player's normal Roblox avatar when no approved TinyWorld character asset exists;
- retain server-authoritative appearance preference persistence without pretending unavailable visual assets are rendered.

### World text

- remove large always-on-top ordinary-world BillboardGui information walls;
- remove prototype copy such as Home Gate, Home Style, Home Supply, Daily Fountain, Village Fund and Profession Board from floating runtime panels;
- use physical/diegetic signage only where a proper noun still needs text;
- keep contextual ProximityPrompt copy short and local to the action.

### HUD

- remove full-width website-like navigation/status treatment;
- remove permanent system-dashboard presentation from normal play;
- keep compact coins/level/current-task/navigation/toast information only.

## Workstream B - Hero visual rebuild

Priority hero objects:

1. player presentation;
2. Town Hall;
3. Village Shop;
4. Home Store;
5. Courier Depot;
6. daily fountain;
7. profession/jobs board;
8. starter-home exterior;
9. starter-home most-touched interior objects;
10. Tiny Bike / primary ordinary travel object;
11. Giant Kitchen entrance;
12. Moonlit Meadow entrance.

Each hero object must pass silhouette, scale, material and feedback checks. Semantic attributes or labels cannot compensate for an unreadable object.

Native Roblox parts remain acceptable when they create a convincing authored object. Hero-tier fallback cannot remain anonymous geometry merely because no external asset has been approved.

## Workstream C - One golden ordinary-life route

v0.6.1 concentrates polish on one complete route rather than adding systems:

`spawn -> understand HUD -> identify home -> enter home -> use a recognisable object -> walk to Courier Depot -> complete a visible delivery -> earn coins -> use Home Store -> buy/place one item -> rejoin and see continuity`

Existing systems outside this route remain functional but do not expand unless a regression must be fixed.

## Workstream D - Evidence and benchmarks

Player-facing visual changes require observed evidence before the release becomes merge-ready.

Required evidence includes:

- character front/side view;
- normal HUD;
- village centre with labels hidden;
- Town Hall;
- Village Shop;
- Home Store;
- Courier Depot;
- daily fountain;
- starter-home exterior/interior;
- primary portal entrances;
- complete golden-route observation;
- phone layout/performance;
- controller focus where the route uses modal UI.

Benchmark files live under `docs/quality/benchmarks/v0.6.1/` and must come from the exact candidate, not generated placeholders.

## Permanent process correction

v0.6.0 demonstrated that source implementation and visual acceptance can drift apart if player-facing work merges while all rendering evidence stays PENDING.

For v0.6.1 and later player-facing releases:

1. source/build CI remains necessary but cannot prove visual quality;
2. required Studio/device visual rows may be NOT RUN while a PR is draft;
3. a player-facing PR is not merge-ready while its required visual rows remain NOT RUN/PENDING;
4. FAIL is useful evidence and produces a bounded backlog item;
5. no release claim may be stronger than its observed evidence.

## Explicit cuts

v0.6.1 does not add:

- new portal worlds;
- profile schema changes;
- new trading classes;
- monetisation;
- a UI framework;
- new runtime dependencies;
- broad career expansion;
- furniture catalogue growth merely to increase counts.

## Exit criteria

v0.6.1 is complete when:

- primitive head/foot character geometry is absent from normal play;
- ordinary village information walls are absent;
- HUD leaves the world visually dominant;
- primary civic destinations and starter home are recognisable labels-off;
- the golden route works end to end;
- required Studio screenshots/route evidence pass for the exact candidate;
- phone/controller evidence is recorded for the golden route;
- canonical docs identify v0.6.1 and the strengthened visual contract;
- automated Luau/analysis/format/compile/release/build gates pass;
- Graphite Mountain integrated review has no blocking finding;
- Cave Pony final audit has no blocking unnecessary visual machinery.

## Release relationship

v0.6.1 is an inserted corrective release. The planned v0.7.0 Village Life release remains next, but it inherits this visual-quality baseline instead of deepening a village that still looks like a prototype.
