# TinyWorld v0.7.6 Runtime Hardening Design

**Status:** Approved design for implementation
**Date:** 17 August 2026
**Baseline:** `main` at `3adce63990f4efab2986250f23cc2cea53a08971`
**Parent audit:** #36
**Branch:** `fix/v0.7.6-runtime-hardening`

## Goal

Turn the findings in #36 into a production-hardening release that closes concrete runtime safety, multiplayer, world-authority, onboarding, test-evidence, performance-governance and product-completion gaps without rewriting TinyWorld's proven persistence, gameplay, release or published-rendering foundations.

The release is intended to advance TinyWorld to `v0.7.6` with a candidate identity centred on runtime hardening. It may publish to Roblox DEV after exact-head CI is green and merge succeeds. It must not publish LIVE.

## Non-negotiable constraints

- Preserve the R5 published-runtime safety boundary: no published runtime `EditableMesh`.
- Preserve Studio-only preview behaviour where already approved.
- Preserve the free-only GitHub Actions workflow.
- Preserve DEV/LIVE DataStore separation and manual LIVE promotion.
- Preserve profile schema compatibility unless a schema change is genuinely required. Prefer no schema bump for this release.
- Do not invent Roblox asset IDs.
- Do not re-enable retired R6/R7 visual presentation paths.
- Keep server authority for economy, rewards, purchases, placement, trading and persistent player mutations.
- Keep alternate portal worlds out of village coastal recovery while a valid portal session is active.
- Human visual and device acceptance remains a release gate after DEV publication.
- Fix every code-owned finding from #36. Only genuinely external asset, device or human-evidence dependencies may remain open, and those must be logged explicitly rather than described as complete.

## Chosen architecture

Use targeted runtime hardening rather than either independent ad-hoc patches or a whole-game rewrite.

The central change is to move cross-service state decisions into small deterministic shared-rule modules that can be executed by the existing CLI Luau test runner. Services remain responsible for Roblox Instances, Player lifecycle hooks and presentation, but rules decide whether a player is in a recoverable traversal state, whether onboarding permits gameplay, whether an activity lease is still valid, and how transient portal state is reset.

This gives TinyWorld a behavioural safety net without introducing Knit, Roact, ProfileService, Wally or another framework.

## Workstream 1: Traversal and portal lifecycle safety

### Problem

R8.1 coastal recovery currently has an out-of-bounds region where recovery becomes a no-op. Portal state also survives character replacement because portal lifecycle is not reconciled on `CharacterAdded`, and traversal safety trusts the portal-world attribute as an exemption.

### Design

Create a deterministic traversal safety decision boundary in shared code. It receives the player/world state needed for the decision and returns an explicit action such as:

- `allow`
- `recover-shore`
- `recover-world`
- `portal-exempt`

The rule must never return `allow` for an ordinary Village player who is outside the canonical coastal gameplay boundary. Message throttling is presentation-level and must never disable the recovery action.

Portal session state remains server-owned. `PortalService` will register character lifecycle handling and reset transient portal state on respawn. A portal reset clears the server session, portal counters, secret state and `TinyWorldPortalWorld`, then reconciles the player to Village. Only a currently valid server portal session can qualify for the village traversal exemption.

### Acceptance

- Village positions at 391, 511, 570, 571 and 10,000 studs all recover.
- A valid portal session remains exempt while actually in its portal world.
- Enter portal, reset/die, respawn results in `TinyWorldPortalWorld == "Village"` and traversal safety active.
- Bike/boat transient flags cannot create an escape path.

## Workstream 2: Public activity ownership leases and cancellation

### Problem

Pip, Finn and Milo use service-wide owners with no inactivity lease or abandon path. A single player can therefore block an activity indefinitely until completion or leaving the server.

### Design

Create `ActivityLeaseRules` in shared code with one fixed lease duration and deterministic functions for:

- acquiring a free/expired lease;
- refreshing a lease on meaningful progress;
- checking ownership;
- determining expiry;
- releasing ownership.

Each serialized public activity uses the same lease semantics. The service maintains Roblox-specific state but ownership validity comes from the shared rule.

Add a player-facing abandon/cancel path through the existing activity service rather than separate custom logic in each activity. Character reset, player removal, portal transition and explicit abandon release the current activity and any public station lease.

The design deliberately keeps public stations serialized for now. It does not introduce per-player cloned activity stations or queue UI in this release.

### Acceptance

- One player cannot hold a public station beyond the lease without progress.
- Progress refreshes the lease.
- Leaving, respawning, portal transition and explicit abandon release ownership.
- A second player can acquire an expired/released station.
- The first player can abandon one activity and start another without rejoining.

## Workstream 3: One authoritative R8 world presentation

### Problem

`WorldBuilder` still creates legacy `VillageSceneryBuilder` and `BoundaryBuilder` presentation before R8 ground/coast are applied. R8 removes only some legacy surfaces. This leaves multiple presentation authorities and coordinate systems alive in the same runtime tree.

### Design

Split the old world bootstrap conceptually into:

1. gameplay anchors/systems that remain required by existing services;
2. presentation that R8 owns.

For this release, avoid a wholesale `WorldBuilder` rewrite. Introduce an explicit R8 retirement/compatibility boundary that removes or suppresses legacy presentation which has been superseded while preserving named gameplay anchors needed by existing services.

At minimum, when R8 is active:

- legacy decorative sea surfaces must not render;
- legacy scenery/path surfaces that conflict with R8 routes/ground must not render;
- gameplay-only anchors must remain functional and invisible where appropriate;
- R8 Terrain coast remains the single visible sea/coast authority;
- R8 ground remains the single visible village ground/route authority;
- no R6/R7 presentation path is re-enabled.

Extend the R8 contract to verify that conflicting presentation cannot remain active indirectly through `WorldBuilder` or `BoundaryBuilder`, rather than only grepping selected direct calls from `Main.server.luau`.

### Acceptance

A runtime/source contract can demonstrate exactly one ground/coast presentation authority and no visible legacy sea/path presentation retained beneath R8.

## Workstream 4: Server-authoritative onboarding phase

### Problem

The client blocks movement during onboarding, but server gameplay systems are initialized and generally only check whether a profile exists. A hostile or modified client can therefore attempt normal persistent gameplay before onboarding is complete.

### Design

Create a deterministic `PlayerPhaseRules` module with an explicit `canEnterGameplay(profile)` decision based on durable onboarding state.

Gameplay systems that mutate persistent state or grant rewards must respect this server-side phase gate. Do not scatter bespoke onboarding checks everywhere. Add a central helper/service boundary that existing handlers can call consistently.

Presentation-only reads and setup UI can remain available. On `CharacterAdded`, the server reconciles the player's phase so respawn cannot bypass onboarding.

### Acceptance

A player with `onboardingComplete == false` cannot earn currency, start persistent activities, buy transport, trade, mutate home state or complete portal rewards. Completing onboarding durably switches the server phase without requiring a rejoin.

## Workstream 5: Behavioural CI, performance and repository protection

### Problem

The current 43 shared-rule specs and source/grep contracts do not execute the cross-service state behaviours that produced the blockers in #36. All portal worlds are eagerly constructed, streaming/performance evidence is not reproducibly captured in the repository, and `main` does not currently enforce the TinyWorld CI status as a required branch check.

### Design

Keep the existing free-only Actions workflow and add behavioural coverage in layers:

- move state decisions into deterministic shared modules and test them directly;
- add service-facing state-machine tests where dependencies can be represented as simple fakes/data rather than Roblox Instances;
- add release/source contracts for world-authority absence, not just required presence;
- retain manual published-client checks for genuinely Roblox-only behaviours.

Do not add a paid testing service, retained workflow artifact, external SaaS or large framework.

Performance governance becomes explicit:

- document the intended `StreamingEnabled`/world-loading decision;
- source-control the setting where Rojo place representation supports it, otherwise document the exact Roblox experience setting as a release prerequisite;
- add a repeatable DEV performance evidence checklist covering instance count, memory, load time, FPS and Developer Console cleanliness on the agreed mobile target;
- do not claim mobile performance passed without real-device evidence.

Lazy-loading portal worlds is conditional, not automatic. First measure. If eager construction fails agreed thresholds, a later scoped change may move portal presentation behind a loading boundary.

Repository protection is part of this workstream. Configure `main` so TinyWorld CI is a required status check before merge if the connected GitHub permissions/tooling expose that capability. If the API surface available in this session cannot change branch protection, log a dedicated operational issue containing the exact manual setting required and leave that audit item open rather than claiming it fixed.

### Acceptance

- Regression tests fail if the 511-stud traversal bug, stale portal respawn state, indefinite activity ownership or server onboarding bypass are reintroduced.
- CI remains free-only and green.
- Performance decision and evidence procedure are reproducible from the repo.
- TinyWorld CI is enforced as a required `main` merge check, or a clearly logged external repository-settings dependency remains open.
- Human/device evidence remains visibly pending until supplied.

## Workstream 6: Product and UX completion

### Character expression

Current appearance preferences are safe but not visibly applied. Preserve the rule against primitive fallback avatar geometry. Complete every code-owned part of visible character expression that can be implemented using approved, already-owned Roblox-safe assets and platform-supported avatar mechanisms without inventing asset IDs.

Before implementation, inspect the checked-in asset registry/manifests and current experience-owned assets. If no approved character assets are available, create a dedicated asset-dependency issue under #36 recording exactly what asset roles are required, keep the existing normal Roblox avatar as the safe fallback, and do not claim the visible-character finding is closed. The release must still improve the code boundary so approved assets can be applied deterministically once supplied.

### Tiny Boat

The current Tiny Boat is an anchored teleport/ferry mechanic, not a genuine traversal mode. `v0.7.6` will replace that primary travel behaviour with a bounded controllable Tiny Boat.

The boat design is deliberately constrained:

- server owns authoritative mounted/active state and validates the resulting navigation zone;
- client sends steering/throttle intent only, never authoritative position, velocity, reward or destination;
- steering/throttle inputs are finite, range-clamped and rate-limited;
- movement is bounded to the canonical coastal navigation area and cannot bypass traversal recovery;
- mount, dismount, death, respawn, player removal and portal transition clear boat control state safely;
- the player must be able to travel physically from the dock toward the outer-coast delivery destination/cove and return;
- direct teleport-to-cove is removed as the primary mounted travel mechanic;
- if unrestricted Roblox vehicle/network-ownership physics proves unstable, prefer a deterministic server-controlled movement model over client-authoritative or unbounded physics.

Add deterministic movement/input/state tests plus a source contract that fails if `_mount()` once again teleports the player directly to Tidepool Cove as the primary journey.

**Tiny Boat acceptance:** a player can mount, steer through the permitted water zone, reach the coastal delivery/cove area, return, and dismount without using a destination teleport as the normal journey. Another player cannot steer the owner's boat, and malformed input cannot move it outside authoritative bounds.

### Mobile/controller UI

Close code-level gaps that are deterministic and low-risk: explicit controller focus ordering for the compact navigation/modal surfaces, safe-area-aware placement where missing, and consistent 44x44 minimum interactive targets. Real phone/controller acceptance remains human evidence.

### Analytics

Preserve the small allow-listed taxonomy. Add only missing high-value lifecycle events required by the target state, particularly first meaningful activity/churn boundary if the current runtime can emit them without free-form data. Do not add sensitive text or high-frequency telemetry.

### Governance

Update #26/#31 and release documentation so v0.7.6 runtime-hardening status is not confused with the earlier v0.7.4/R8 lifecycle. #36 remains the parent audit; focused workstream issues carry implementation acceptance.

Use one implementation branch for the coordinated runtime-hardening release so cross-service invariants can be verified together. Commits should still be small and workstream-oriented.

## Testing strategy

Every behavioural fix follows Red → Green → Refactor.

Minimum new regression cases:

### Traversal

- inside boundary
- 390 edge
- 391 outside
- 510
- 511
- 570
- 571
- 10,000
- valid portal session exemption
- stale portal attribute without valid session does not exempt

### Portal lifecycle

- enter each portal
- reset character
- state returns to Village
- counters/session cleared
- traversal protection restored

### Activity leases

- acquire
- reject second active owner
- refresh on progress
- expire
- release
- abandon
- release on respawn/leave/world transition

### Onboarding

- incomplete profile rejected from persistent gameplay mutation
- completed profile allowed
- transition after successful onboarding takes effect immediately

### World authority

- R8 source/runtime contract rejects legacy visible sea/path presentation when R8 active
- required gameplay anchors remain present

### Tiny Boat

- owner can start/stop control session
- non-owner cannot control boat
- throttle/steering are finite and clamped
- movement remains inside coastal navigation bounds
- respawn/leave/portal transition stops control
- normal mount path does not teleport directly to the destination

### Existing regression

All current shared specs, Luau analysis, formatting, runtime compile, R8/R8.1 contracts, release contract, build contract and published-safe rendering checks remain green.

## Human acceptance remaining after code completion

No amount of CI substitutes for these checks:

- current exact build stamp visible in Roblox DEV;
- desktop hero-village screenshots;
- phone portrait and landscape;
- controller navigation;
- two-player activity lease recovery;

- agreed mobile FPS/memory/load evidence;
