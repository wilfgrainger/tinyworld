# TinyWorld v0.0.6 Persistence and Scale Test

**Status:** Evidence route for queue/session hardening  
**Scope:** DataStore safety, local capacity, and bounded multiplayer evidence

This route is intentionally explicit about the difference between local Studio evidence and production-scale proof.

## Prerequisites

1. Use the published private TinyWorld Dev experience.
2. Enable Studio Access to API Services in Experience Settings → Security.
3. Start \`rojo serve\` from the repository root and connect the Studio plugin to \`localhost:34872\).
4. Keep Output visible.
5. Record the Git SHA, place name, and Studio session time.

## Queue/coalescing route

In one session, perform several mutations close together:

1. Claim the fountain reward.
2. Plant and water a garden bed.
3. Start and deliver a Courier job.
4. Buy or toggle the Tiny Bike.
5. Collect a living-world pickup.
6. Visit a boundary landmark.
7. Complete a trade when two clients are available.
8. Inspect the player attributes:
   - \`TinyWorldSaveState\`
   - \`TinyWorldSaveVersion\`
   - \`TinyWorldSaveRetryAttempt\`
   - \`TinyWorldSessionState\`

Expected result:

- The state may move through dirty/queued/saving/clean.
- Multiple mutations should share a coalesced save rather than create one immediate write per action.
- Retry state is visible if Roblox returns a transient DataStore failure.
- No DataStore queue warning should be produced by the normal short route.

## Stop/rejoin persistence route

1. Perform the route above.
2. Stop Play cleanly.
3. Press Play again with the same profile.
4. Compare visible identity, coins, level/XP, inventory, house tier, Courier state, bike ownership, garden state, portal completion, boundary state, privacy, and life-kit values.

A failed load must fail closed. A missing or inaccessible profile must not become a new default profile.

## Session conflict route

Use only a permitted test arrangement that does not expose a live account or production data:

1. Start one server with a test account and allow it to acquire the profile lease.
2. Attempt to join the same test account/session through the approved second-session route.
3. Confirm the competing session cannot overwrite the active profile.
4. Confirm the rejected session receives the safe rejoin message.
5. After the original session ends and its lease is released or expires, confirm a later join can acquire the profile.

Record the exact behaviour; do not treat a blocked account login as proof if the second session did not reach the profile adapter.

## Shutdown route

1. Use Server & Clients with multiple local clients.
2. Perform a mutation for each client.
3. Stop the server.
4. Record any unresolved save warning and the final save/session attributes visible before shutdown.
5. Repeat once after a clean run to distinguish a transient Studio failure from a reproducible defect.

## Evidence boundary

- Luau rules and source guards prove contract behaviour.
- Studio Server & Clients proves bounded local behaviour.
- This route does not prove cross-server latency, live DataStore quota under production load, or a 60-concurrent-user production run.
- Those claims require a separately authorized production test.
