# TinyWorld v0.7.6 / ART R8.2 DEV Performance Acceptance

Status: **PENDING REAL DEVICE**

This document is the human runtime evidence gate for TinyWorld v0.7.6 / ART R8.2. Source, unit, compile and build checks can prove that the performance policy is present and reproducible, but they cannot prove real Roblox client performance. Do not mark this document PASS until the current DEV place version has been measured on real target hardware.

## Source-controlled streaming baseline

TinyWorld uses Roblox instance streaming as a conservative baseline:

- `Workspace.StreamingEnabled = true`
- `Workspace.StreamingMinRadius = 64`
- `Workspace.StreamingTargetRadius = 1024`
- Rojo preserves unknown Workspace children rather than deleting Studio/runtime content that is not mapped by the project file.

These values are a baseline, not a tuning victory. Do not reduce radii or introduce more aggressive streaming behaviour without measurements showing a specific bottleneck and a published-client retest.

## Hard acceptance budgets

The current target-state budgets are:

- sustained representative gameplay: **at least 30 FPS**;
- measured Roblox client memory: **no more than 500 MB** for the agreed acceptance run;
- fresh join to playable state: **no more than 15 seconds**.

The deterministic `PerformanceBudgetRules` module mirrors these thresholds and fails closed when evidence is incomplete. Runtime evidence remains authoritative for the device gate.

## Required runtime route

Use the same representative route for each performance run:

1. cold/fresh join and spawn into the village;
2. walk the main village hero route and central civic area;
3. visit Gardener, Fisherman and Builder activity destinations;
4. reach the coast, enter/exit the Tiny Boat flow and deliberately approach authored traversal bounds;
5. enter each available portal world and return;
6. perform a representative two-player session including activity contention/release;
7. revisit the village after portal travel so streamed content recovery is observed.

## Evidence to capture

Capture or record all of the following for the exact DEV build:

- FPS using Roblox Performance Stats through representative gameplay, including the lowest sustained interval;
- memory from the Roblox Developer Console / memory view, recording exactly what the Roblox tool reports rather than estimating TinyWorld-only memory;
- fresh load time using a repeatable timer from join initiation to controllable/playable state;
- runtime **instance count** at representative village and portal-world points, using a reproducible Studio/client diagnostic method and recording the method used;
- Developer Console errors and warnings, with new TinyWorld runtime errors treated as a failure;
- a Roblox **MicroProfiler** capture for the worst observed performance section and notes on the dominant frames/tasks;
- any visible streaming pop-in, delayed collision, missing interaction target or return-to-village reconstruction problem.

## Failure handling

If a budget fails, diagnose the measured bottleneck before changing architecture. In particular, inspect the cost of eagerly constructed portal-world presentation and runtime instance counts before blindly shrinking streaming radii. If evidence shows that eager world construction is the dominant cost, prefer lazy construction, authored prefabs or separate-place/world loading based on measured impact.

A green GitHub Actions run does not close this document. It becomes PASS only when the current published DEV build has complete real-device evidence at or inside all three hard budgets and no new Developer Console/runtime correctness failure appears during the route above.
