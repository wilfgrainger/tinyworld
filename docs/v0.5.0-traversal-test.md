# TinyWorld v0.5.0 traversal expansion test

v0.5.0 turns the existing sea boundary into a small physical journey. It adds
a persistent Tiny Boat for 600 earned coins, a visible Sea Dock purchase and
boarding route, and a physical Tidepool Cove with a return dock. It does not
add a new currency, item reward, premium gate, combat system, or progression
advantage.

The physical-affordance rule is part of this release gate: anything received
must be represented by a physical pickup, visible Item Chest/table object, or
an immediate named popup. A profile attribute by itself is not evidence of an
item or vehicle.

## Local source gate

Run these commands from the repository root:

```powershell
luau tests/run.luau
& "C:\Users\wilf6\scoop\apps\luau\current\luau-analyze.exe" src/shared/*.luau tests/*.luau
$compiler = "C:\Users\wilf6\scoop\apps\luau\current\luau-compile.exe"
Get-ChildItem src/server -Filter *.luau | ForEach-Object { & $compiler $_.FullName > $null; if ($LASTEXITCODE -ne 0) { throw $_.Name } }
Get-ChildItem src/client -Filter *.luau | ForEach-Object { & $compiler $_.FullName > $null; if ($LASTEXITCODE -ne 0) { throw $_.Name } }
powershell.exe -NoProfile -ExecutionPolicy Bypass -File tests/verify-traversal.ps1
powershell.exe -NoProfile -ExecutionPolicy Bypass -File tests/verify-physical-affordance-invariant.ps1
powershell.exe -NoProfile -ExecutionPolicy Bypass -File tests/verify-item-reward-contract.ps1
powershell.exe -NoProfile -ExecutionPolicy Bypass -File tests/verify-physical-items.ps1
powershell.exe -NoProfile -ExecutionPolicy Bypass -File tests/verify-roblox-materials.ps1
rojo build default.project.json -o "$env:TEMP\tinyworld-v0.5.0.rbxlx"
git diff --check
```

Expected source output includes `TinyWorld tests passed: 23 specs`, a clean
server/client compile loop, both physical-affordance guards passing, a material
guard pass, and a Rojo place artifact.

## Rojo and Studio setup

1. From `C:\Users\wilf6\dev\tinyworld`, run `rojo serve`.
2. Open the authenticated `TinyWorld Dev` place in Roblox Studio.
3. Use the Rojo Studio plugin to connect to `localhost:34872`.
4. Confirm the synced `ServerScriptService.TinyWorld`,
   `ReplicatedStorage.TinyWorld`, and `StarterPlayer` source trees are present.
5. Keep Output visible while testing. All source changes must flow through
   Git and Rojo; do not edit source in Studio.

## Single-player route

1. Press Play and confirm the HUD reads `TINYWORLD | v0.5.0 TRAVERSAL` and
   shows both Bike and Boat transport state.
2. Visit the physical `TINY BOAT DOCK` at the Sea Dock. The dock, sign, kiosk,
   and purchase prompt must be visible in the world.
3. With at least 600 coins, use `Buy Tiny Boat`. Confirm the popup names the
   purchase and the real Tiny Boat model appears beside the dock with a
   `Board Tiny Boat` prompt.
4. Board the boat. Confirm the player arrives in the physical Tidepool Cove,
   sees its island, meadow, dock, beacon, and story marker, and sees the boat
   model there with `Return to Sea Dock` available.
5. Use the physical return prompt. Confirm the player returns to the village
   Sea Dock and the same boat model is parked there.
6. Stop and rejoin. Confirm ownership remains in the HUD/profile, the boat is
   parked at the Sea Dock, and the player is not stranded in the cove.
7. Exercise one existing item path in the same source revision. For a daily
   reward or harvest, confirm the named popup and the owner's physical Item
   Chest/table display both show the item. For a village find, portal find, or
   trade, confirm the world object/prompt and named result popup are present.
8. Stop again and inspect Output. A Rojo disconnect or the known Studio
   DataStore queue/competing-session warning is a separate test dependency;
   any red source/runtime exception is a failure.

## Evidence boundary

The local gate proves pure boat rules, schema-v10 migration, source wiring,
physical world contracts, compilation, material safety, and Rojo assembly. A
single-client Studio run proves local runtime integration only. If a
command-bar teleport is used to position the player, record it as a positioning
aid and do not count it as normal-route movement evidence.

Publishing the Rojo-synced place proves that Studio accepted a save. It does
not by itself prove live-experience parity. Record the source commit, Studio
save confirmation, and a separately reopened published target before claiming
published parity. Two-client fairness, cross-server persistence, production
capacity, and family/device comprehension remain separate gates.
